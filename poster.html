Motivation

Transformer attention is the dominant compute bottleneck in modern LLMs. Efficient kernels for its three sub-operations — QKV projection, QK dot product, and attention-value (AV) sum — directly determine end-to-end inference latency at every scale.

Research question: Can TVM MetaSchedule auto-tune Tensor Core WMMA kernels that match or exceed hand-optimized cuBLAS on an NVIDIA L40S?

This project performs operation-level isolation — measuring each attention component separately — and goes beyond black-box timing to analyze generated CUDA kernel assembly and explain performance gaps mechanistically via inspection of cp.async, WMMA fragment counts, and thread-block sizing.

Key innovation: A single shared projection kernel is tuned once for Q, K, and V — reusing one compiled artifact for all three projections rather than redundantly tuning three near-identical GEMMs.

Kernel Implementation Deep-Dive

TVM WMMA Pattern (Blocking)

All 15 auto-tuned kernels use nvcuda::wmma 16×16×16 FP16 fragments. Critical limitation: not a single cp.async instruction across all kernels. Every HBM load blocks the warp before compute can proceed.

Inspection result: cp_async = 0 across all 15 kernels.
Memory latency (~400–600 ns per L2 miss) is fully exposed on every inner-loop iteration.
// Load A & B tiles → shared memory
*(uint4*)shmem[off_a] = *(uint4*)(A+ga);
*(uint4*)shmem[off_b] = *(uint4*)(B+gb);
__syncthreads(); // FULL BARRIER — all loads must
// complete before any compute

wmma::load_matrix_sync(A_frag, &shmem[a_base], ld);
wmma::load_matrix_sync(B_frag, &shmem[b_base], ld);
wmma::mma_sync(C_frag, A_frag, B_frag, C_frag);

cuBLAS Pattern (Async Pipelined)

cuBLAS on sm_89 uses software pipelining (double buffering) with cp.async — prefetching the next tile asynchronously while Tensor Cores compute on the current tile. Memory latency is completely hidden.

cp.async double buffering hides every HBM load behind Tensor Core computation. Average HBM latency (~400–600 ns) never appears on the critical path.
// Prefetch NEXT tile while computing CURRENT tile
cp.async.cg.shared.global [shmem_A_next],
[gmem_A_next+step], 16; // async — non-blocking
cp.async.commit_group;

wmma::mma_sync(C, A_curr, B_curr, C); // compute

cp.async.wait_group 0; // wait only at stage flip
__syncthreads();
swap(shmem_A_curr, shmem_A_next); // flip buffers
Why the gap closes at Llama-2048: At hidden_dim=4096 and seq=2048, both kernels saturate the L40S at ~330 TFLOPS FP16 compute ceiling. The memory overhead is amortised over so many FLOPs that pipeline differences become secondary.

Why TVM wins on QK/AV loops: PyTorch's Python for h in range(num_heads) loop incurs 3–8 µs CUDA launch overhead per head iteration (×12–32 heads × 200 benchmark iters). TVM compiles all logic into a single kernel launch eliminating this overhead entirely.

Key Findings

Where TVM MetaSchedule Wins

  • Eliminates Python loop launch overhead for per-head dot products. PyTorch's torch.matmul in a Python for h in range(32) loop fires 32 separate cuBLAS calls per forward pass — each costing 3–8 µs. TVM compiles this into one kernel launch.
  • Problem-matched thread blocks: QK_dot_Llama_128 uses exactly 32 threads (one warp) for a tiny 128×64 per-head GEMM — matching occupancy to actual parallelism where cuBLAS would over-provision.
  • Consistent Tensor Core exploitation: 100% of kernels use 16×16×16 FP16 WMMA fragments — correct use of the L40S's Ada Lovelace hardware.
  • Best-case 1.97× speedup on Llama-512 QK dot — the ideal regime where sequence-level parallelism creates launch overhead and problem size still fits in L2 cache.

Where TVM MetaSchedule Loses

  • No cp.async pipelining — the single defining structural bottleneck. MetaSchedule's search space does not include async-copy schedule templates, exposing full HBM latency on every K-reduction inner-loop step.
  • QKV projection always slower (0.57×–1.00×): At hidden_dim=4096 the projection GEMM has K=4096, yielding 128 outer loop iterations in proj_Llama_2048 — accumulated exposed memory latency adds a measurable deficit.
  • AV sum reverses at Llama-2048: The per-head attention-value multiply becomes a (2048×2048) × (2048×128) GEMM — large enough for cuBLAS's async copy advantage to overcome its launch overhead (0.94×).
Practical recommendation: For LLM KV-cache decoding (short sequences, many head iterations), TVM reduces per-head loop costs by 1.2×–2.0×. For prefill with long context, Flash Attention (SDPA) is 1.6×–4.4× faster than any unfused approach regardless of kernel backend. The QKV projection GEMM should remain with cuBLAS until MetaSchedule supports cp.async pipelined schedules.
Conclusions & Future Work

What We Demonstrated

TVM MetaSchedule auto-tuned WMMA kernels beat PyTorch/cuBLAS by up to 1.97× on per-head QK dot product loops at small-to-medium sequence lengths by eliminating Python kernel-launch overhead accumulated over 12–32 attention heads. At Llama-512 the full three-stage pipeline runs 1.39× faster. The advantage converges to parity at Llama-2048 scale, where problems saturate the L40S compute ceiling and both backends hit ~330 TFLOPS.

Root Cause & Bottleneck

A single structural absence explains TVM's QKV projection loss across all five workloads: zero cp.async instructions in any of the 15 generated kernels. cuBLAS maintains double-buffered shared memory with asynchronous prefetch, completely hiding 400–600 ns HBM loads behind Tensor Core compute. Extending MetaSchedule's search space to include async-copy pipelined schedule templates would directly close this gap without any algorithmic change.

Future Directions

① Fused FlashAttention TVM kernel — implement tiled streaming attention to eliminate the (seq×seq) HBM round-trip, the only way to close the 1.6×–4.4× SDPA gap.
② MetaSchedule + cp.async — add async-copy schedule templates to the MetaSchedule search space on sm_80+ targets.
③ INT8 / FP8 Tensor Core — evaluate mixed-precision attention feasibility on the L40S's 660 TOPS INT8 peak, potentially doubling throughput at acceptable accuracy loss.
④ Decode-mode KV-cache — apply TVM loop fusion specifically to the incremental decode path where short sequences and many head iterations most favour auto-tuned kernels.
